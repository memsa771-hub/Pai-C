# Vault intake and domain stewardship

All student channels use the same write boundary:

`conversation / voice / profile / document -> MemoryCandidate -> VaultAssertion + VaultEvidence -> domain steward -> MemoryReconciler -> VaultFact / typed record`

An assertion records what a source claimed, including a rejected or disputed claim. It does not make the claim true. The reconciler alone changes canonical state. Evidence records are deduplicated by source reference, locator and quotation; an assertion links to evidence without copying it into another evidence row. Existing candidate and canonical evidence JSON remains readable for older callers. A claim's `effective_at` is the asserted time of the real-world change; `captured_at` is when PAI learned it. Unknown effective times stay null.

The extraction model handles arbitrary language and proposes schema-shaped candidates. `RecordDomainSteward` resolves existing entities from the shared record identity/discriminator contract and checks student-voice attribution and conflicts. It cannot write canonical data. Vault scalar field definitions keep versioned validation, source and temporal policies as data. A field with `source_policy.allowed_sources` rejects an unauthorized source; `authority_rank` can override the legacy global ranking for that field. A student transition is accepted only for a field configured with `source_policy.temporal_change = "student_transition"` and a student-sourced claim explicitly marked as a temporal change. Otherwise disagreement remains a Profile issue.

`VaultRelation` stores explicit cross-domain edges. Course containment remains the existing `CourseRecord.education_id` foreign key. The current read model creates `project demonstrates skill` only when both canonical records exist and the project's named skill matches exactly and unambiguously. It retires stale edges after a relevant update. Other relationships should be proposed through `VaultRelationService.link`, which checks that both endpoints and the accepted supporting assertion belong to the same workspace.

The shared text/voice Counselor uses `counseling/context_projection.py` on every turn. It starts from the counseling-safe `StudentUnderstandingBuilder` view, keeps a small identity/education/goal baseline, ranks other visible records against the current message using Unicode token overlap, and includes only links whose two endpoints are selected. This is a bounded read-time projection of accepted Vault data, not a second memory or a new source of truth. Education chronology and course containment come from the existing Understanding view and course foreign key; they are not persisted as new `VaultRelation` rows. The Counselor can therefore use connected student context without sending the full graph, raw IDs, sensitive identity fields, or Profile machinery to the model.

Generic credentials use `StudentCredential`, with issuer, dates, format, identifier, document reference and bounded claims. A document's `raw_document_ref` is assigned by the document job, and reconciliation checks the file belongs to the student. A stored credential is **not** treated as cryptographically verified: document support and cryptographic verification are separate statuses. Credential identifiers and raw assertions are not included in routine Counselor context or the Profile projection.

Adding a scalar field means adding a versioned `VaultFieldDefinition` with validation, sensitivity and source policy. Adding a repeatable record kind means defining its schema/identity contract, model and migration, then choosing its Counselor/Profile projection explicitly. Keep semantic interpretation in the extraction layer and canonical authorization in the reconciler.

Design references: [W3C PROV-O](https://www.w3.org/TR/prov-o/) distinguishes entities, activities, agents and derivations; [W3C Verifiable Credentials Data Model 2.0](https://www.w3.org/TR/vc-data-model/) separates issuer claims from a verifier's policy; [Open Badges 3.0](https://standards.1edtech.org/open-badges/specifications/standards/v3p0/) aligns educational achievement credentials with VC 2.0. The current Vault preserves these distinctions without claiming to implement VC proof verification or a graph database.
