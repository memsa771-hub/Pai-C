# Locked workflow implementation decisions

## Execution

The founder authorized autonomous completion on pai-c. Clear implementation,
fixture and prompt-document fixes have no attempt limit. Existing coverage stays.
No live providers, dotenv edits, table drops or shared-code deletion are allowed.

## Factual cards

Choices come only from schema/catalog data. Every catalog card supports editable
Other. Missing catalogs use text or an upload invitation; no invented options are
seeded. Prefills require an exact quote from the current student message and
explicit confirmation. Other values retain stated evidence and a review flag.
Coverage may require several distinct facts in one area. The existing
question-intent and policy repetition guards remain responsible for repeated questions.

## Shared OS contract

tasks.list, tasks.create and workflow advancement stay pending OS developer
agreement. Browser backend, integration relay/settings, notifications, all
models/tables and shared registries remain.

## Evidence confirmation

Confirmation reviews the exact active value, protected by a digest and a
workspace lock. A stale card requires reload. Idempotent reviews use existing
candidate evidence; no table is added. Confirmed is a separate evidence label,
not an external credential-verification claim. Record reviews cover the complete
displayed record; changing it invalidates the digest. Edits return to stated.
Document-supported/externally verified provenance remains shown. Restricted
Vault fields are excluded using the existing safe profile projection.

## Knowledge

The existing RequirementStore remains the cache. Authoritative season bounds
supplement its TTL; absent calendars do not invent a season. Merit rules require
an explicit reviewed program/season rule. The shipped catalog is empty.
Voice declares specific world assertions with fact ids. The guard requires an
exact current sourced value/quote, appends source/date, and removes unsupported
assertions and numeric currency/percentage claims. Student evidence is exempt.
No extra foreground model call is introduced. General explanations remain model
generated; deterministic validation cannot identify every unannotated qualitative
claim. That residual quality limitation is recorded for the founder evaluation.

## Phase 2, step 5: paths before places
Mirror confirmation now materializes evidence-backed possibilities without delegating institutional research. Explore queues `path.explain` through the same Research Gateway and durable Operator workflow. A repeated request reuses its run per possibility and Mirror version. Existing stale-refresh and student-answer jobs retain their behavior.
The general explanation is validated separately from sourced world claims. Fit quotes must exist in the supplied student evidence. Jobs, myths and outlook without verified sources remain unavailable, never asserted as facts. All web work remains budgeted and the model uses the existing gateway.
Regression tests for confirmation now assert no Operator run; the old payload/dedupe test exercises the preserved student-answer research trigger. Architecture assertions are unchanged: delegation still has a single call site.

## Phase 2, step 6: explicit program search
`program.search` is a native workflow composing existing `program.discover` and `program.research`, one capability nesting level. A POST with explicit consent and a completed current-Mirror path run is required; GET never initiates research. Runs reuse the path+Mirror key and student budget. Missing destination evidence produces a missing-information result, not a guessed country.
Eligibility uses shown/confirmed values only. Meeting entry rules is labelled eligible, not safe: safe/realistic/stretch require an independently reviewed program+season rule. Not-yet routes use only cited remediation. Existing research cache and SourceVerifier remain the source of facts.

## Phase 2, step 7: private reliability surface
An authenticated workspace health endpoint checks database-backed analysis backlog, a data-configured lag threshold, failed jobs and daily guard/fallback counts. Counts use existing durable turn decisions, with idempotent provider/unconfigured records; no text or credentials are returned. The existing public liveness endpoint is unchanged. Planner lag is an in-app attention state, not a new notification channel or scheduler. There is no provider ping and no paid health call.

## Phase 3: one student shell and existing contracts
The main workspace mounts only Counselor, Journey, Paths, Profile, Compare, Plan,
Documents, Settings and the existing notification center. Four entry cards are
advertised by the backend; old eight-field submissions remain accepted for old
clients. No new institution or exam catalog is invented.
Profile confirmation, editing and removal all create reconciled candidates.
Removal retires an active record with an audit revision; it does not erase its
history. No database table or schema is removed. The existing account-erasure
endpoint is available only after a separate explicit irreversible-deletion
confirmation. The export scope is explicitly described below.
A completed current-Mirror program check may explicitly request a reviewed
roadmap through the existing builder. It does not choose the path. Existing
roadmap choice, decision records and planning remain the authority for I/J.
The initial Phase 3 check-in control opens a draft in the same Counselor. The core continuation below additionally schedules in-app follow-ups through Task Runtime; no OS reminder scheduler is added.
Journey links use durable event ids and page older chat history when necessary.
Screenshots and browser navigation use a separate test-only Vite entry with fake
API/workspace adapters and blocked network access; no fake data is in app routes.


## Final review: freshness, export and inline presentation
Program pages re-read the current workspace's RequirementStore rows and the student's current shown/confirmed facts. Changed routes or expired evidence require another explicit search; pending runs still deduplicate. Expired path world claims are hidden and may be refreshed explicitly. Generic path prose is kept. No GET initiates research and the existing Mirror budget still applies.
The legacy Add goal/program-research shortcut is hidden in the new Compare/Plan surfaces. Reviewed roadmap creation follows a completed path-specific program check; the existing choice-token dialog remains the authority for a student's decision.
A first-picture presentation card and a 0?10 rating control follow the existing policy action/topic. Care overrides both; a rating is a normal student message only after Send, and the Analyst remains the Truth Map writer.
The locked board itself supplies the four named level choices. Those labels are data in entry_fields.json, with editable Other; non-catalog student wording is retained with a catalog-review flag. No board/subject or seasonal threshold is invented.
Public profile sections use explicit data selectors for interests, values, goals and options. The ten coverage keys match the backend (family_social/sure). Capability depth is not presented as evidence verification. Undated education remains visible without an invented date.
The owner-only /v1/counselor/export endpoint exports student-visible data (conversation, profile, paths, roadmaps, confirmed picture, ratings and document metadata), reusing the existing export redactor. Original document downloads remain in Documents. Internal model notes/archives and credentials are excluded. No export or deletion is automatic. Account deletion logging no longer includes an email.
Daily health includes open student requests and noted questions as counts only. The continuation below adds notification delivery through the existing sweep and inbox, without a new scheduler or paid provider ping.

## Core continuation: sourced beliefs, family preparation and follow-ups

- A relevant active `myth.*` item can select `clear_myth` in either policy mode, after care and request handling. Relevance uses the existing classifier's options/goals areas. No country, institution or persona list is used. The same claim is not repeated in every turn; retry spacing is data.
- A durable `research.claim` job is requested through the Research Gateway. Previous successful job results provide the claim cache. It uses the existing budget, search/fetch tools, Model Gateway and SourceVerifier. The claim/evidence fingerprint prevents reuse after the underlying claim changes. Research gets a separate data-configured 30-day budget window, reusing the existing per-student call cap, so it neither spends a future Mirror allowance nor permanently locks out later checks.
- A correction is an exact source passage plus URL and checked date, not an invented paraphrase. Trusted domains come from the existing official registry or `policy/myths.json`; no new trust pack is fabricated. Qualitative passages use the verifier's official-domain, cycle, schema and freshness checks; numeric admissions corroboration is not represented as satisfied by a qualitative quotation. Missing/untrusted evidence leaves the question open. Once a sourced reply is actually posted, its matching request records become answered. Care still wins.
- Family preparation is an explicit guided action: choose a family member, review the recorded wish/worry, and select the student's evidence to discuss. PAI does not claim the selected evidence guarantees an outcome or resolves the worry. The result is saved via Messenger in the same conversation, with submission idempotency and evidence identifiers based on content. No model call is needed.
- The guided action requires a chosen path with completed stage-H results. Legacy choices lacking that proof stay unavailable rather than risk introducing an old institution-bearing title. Students can continue discussing family in normal Counselor chat. The backend rechecks the selected person, concern and evidence at submission, and care blocks this action.
- Choosing a path queues a follow-up after seven days; explicitly accepting a path try-it queues one after three days. These defaults and wording live in `checkins.json`. The existing Task Runtime's `available_at` schedules them, without PAI OS or another scheduler. Retries deduplicate against both the job and posted event. Dismissed/superseded work does not send. Recent conversation, care and another recent check-in defer delivery. No historical choice is automatically backfilled.
- Check-ins are in-app only. Messenger suppresses integration relay for this explicit metadata flag; ordinary messages keep existing relay behavior. Responses continue through the existing student-message/extraction pipeline. Merely viewing a try-it never asserts acceptance or completion.
- The existing session sweep checks reliability thresholds. It enqueues at most one notification per workspace and UTC day, and the existing notification service deduplicates delivery. Counts only are sent to the workspace inbox: no student text, personal interpretation or credentials. This uses existing workspace access rules and does not add a separate administrator broadcast channel.
- Human-readable labels and enum wording live in `frontend/lib/evidence-labels.json`. Unknown schema keys are never printed; student-authored values remain visible. Technical identifiers are omitted from the presentation. Voice controls show one idle Talk to PAI button, with separate connection status only during a session.
- Per the latest instruction, no new test files or extensive feature tests are added. Existing capability inventory is expanded to require the three new registered jobs, and the profile test now selects the public Name label instead of the internal field key. The assertions remain strict. Existing offline screenshot fixtures include the guided family panel.

There is no runtime call to a font CDN, and the offline harness renders the same font as production. The design skill's playful pairing (Baloo/Comic Neue) was rejected as too childish for 15-20 year olds.
- **Shared kit, no variants.** `components/pai`: PageHeader, SectionCard, StatChip, EvidenceBadge, AreaHeatmap, Timeline, QuadrantCard, EmptyState, ErrorState, Skeletons. The chat path suggestion and the Paths page share `PathCardView`. The profile and the chat Mirror share `FeltUnderstood`. Buttons gain touch sizes (`tap`, `tap-icon`, 44px) and a `soft` variant; existing sizes are unchanged for OS screens.
- **Account menu moves to the top bar.** This supersedes the 19 October footer placement because the redesign spec asks for a top bar with a stage chip, notifications and an avatar menu. The menu, its Profile shortcut, theme switch and confirmed sign-out are the same component. On phones a bottom tab bar holds four destinations plus More (bottom-nav limit of five).
- **A-K stage chip is derived on the client.** The backend's internal journey stages are not A-K. Each stage in `copy.json` names a signal (onboarded, a conversation moment, Mirror confirmed, paths found, a path explored, roadmap prepared, roadmap chosen, decision recorded). The current stage is the one after the furthest stage reached. K is ongoing and never "done". Only data the student already has is read; nothing decides for them.
- **Heatmap strength needs one read-only field.** `coverage_areas` now also returns `evidence`, the strongest public evidence level in each area: Vault `evidence_level`, or a notebook item's kind (said maps to stated; shown, document and action map to shown). Same endpoint, same access check, no storage, no model call, never a score. The heatmap shows strength by fill and amount by dots, always with a word, and tapping an area filters the Details view.
- **Details are readable or hidden, never raw.** Vault facts render through `lib/evidence-labels.json` (unknown keys fall back to "Detail"; technical ids are hidden). Date-only values show as calendar days in UTC, so they do not slip a day. Conversation evidence (interests, values, family, pressures, goals, options) is shown read-only under "What you have shared about ..." with "Tell PAI"; only Vault facts get Confirm/Edit/Remove, through the existing digest-checked review endpoint.
- **Private by default.** Family worries, pressures and sensitive keys (date of birth, gender, finance) are masked until the student presses "Show private details". Private interpretation is never fetched.
- **Certainty at decision time.** No backend field records certainty when choosing. The decision card's slider reuses the rating-card pattern: nothing is sent while moving it; pressing Share posts the student's own message ("My certainty about my choice is N out of 10"). Choosing a route still needs the existing confirmation token and dialog.
- **Check-in card.** Opening the conversation from Plan shows a check-in card whose quick starts only fill the draft. Nothing is sent automatically, matching K.
- **Path colours by list order.** Hashing an id into six tones collides often (about 44% for three paths), so paths take distinct tones by their order in the student's own list. The path page and chat read the same order. Other things (people, programs) still use a hash.
- **Eligibility pills.** safe/eligible = green, realistic = blue, stretch = amber, not yet = neutral, unknown = an outlined information pill "Needs checking". Missing research is a calm information state, never an error colour.
- **Harness v2.** `tests/preview/workspace.e2e.cjs` covers light/dark at 375/768/1440, overflow, raw keys, console and page errors, and screenshots (375/1440) to `screenshots/v2`. The crawler clicks every enabled control and link on every screen and fails on dead buttons and unknown routes. Re-selecting the current page or chip is a no-op, and an opened file chooser counts as a response. `flow.cjs` re-proves the A-K boundaries. The fakes can force loading, error and empty states (`?state=`). The v1 screenshots are left untouched for comparison.

## 20 October: three-step onboarding; reply language removed

- **Three steps, all data-driven.** `backend/app/memory/entry_fields.json` now lists seven required fields, and each one names its `step`. Step 1 is first and last name. Step 2 is current or most recent education (Matric, O-level, FSc, A-level, or Other in the student's own words), date of birth and gender. Step 3 is country and city. The frontend groups fields by `step`, so moving a question between steps is a data change, not a code change.
- **Name.** There are no first/last name keys in the Vault. The two parts (`part_of: fullName`) are joined into `identity.full_name`, and the first name is copied to `identity.preferred_name` (`copy_to`), which PAI uses as the greeting and display name. An existing full name is split back into first and last for prefill. No migration is needed.
- **Country.** It is a data default (`default: "Pakistan"`, `options: ["Pakistan"]`), shown pre-selected with the note "More countries are coming soon". Adding countries later means extending `options` (or swapping in a selector); nothing is hardcoded in code.
- **Date of birth.** A custom picker goes year → month → day (fast for a birthday, unlike paging back month by month). It disables future dates, shows the student's age, and sends ISO `YYYY-MM-DD`, which the backend validates again.
- **Reply language removed everywhere.** It was a question, a Settings card, labels and copy, but no counseling logic read it. The `preferences.preferred_language` Vault definition and its migrations stay, so no data is dropped and old facts remain readable. A `replyLanguage` answer sent by an old client is ignored, not rejected (`RETIRED_ANSWERS`).
- **Older clients keep working.** `apply()` still accepts the previous name/level/city shape and the legacy shape. The required set is chosen by which answers arrive.
- **Design.** Onboarding uses the same auth shell as sign-in: form on the left, mascot on the right with a per-step speech bubble. It has a segmented progress bar, a "Step N of 3" label, a validate-on-Continue flow with inline errors and focus, and a short slide between steps (reduced-motion aware). It fits without scrolling at 1440, 768 and 375 in light and dark.

  - experimental agent "monitor mode";
  - the login-enforcement switch and the workspace machine token;
  - Slack, Telegram and Lark bot bindings with tokens, signing secrets and a "default agent";
  - a BrowserFabric API key;
  - a split-browser toggle.
  
  None of these is a student's setting, and showing bot tokens to a 15-year-old would be harmful. Those pages and `components/settings` are removed. `/[workspace]/settings` and any sub-path redirect to `?view=settings`, so old links and the Slack OAuth return still land somewhere real. If operator controls are needed later they belong in an operator console, not the student workspace.

- **Settings layout and contents (founder: professional, not big cards; match the old workspace-settings pattern).** There is a section list on the left (Account, Appearance, Notifications, Privacy & data, Help) and compact rows on the right, in the workspace tokens. Each row has a label and one line of help on the left and its control on the right. On phones the section list becomes a scrolling pill strip. `?section=` deep-links a section.
  - **Account:**
    - Name shows with "Edit in About you", because the name lives in the Vault and a second editable display name would bring back the preferred-name split;
    - Email is read-only;
    - Password sends a reset link through the existing recovery flow (Google sign-ins have no password here, which the help says);
    - Sign out, with a confirmation.
  - **Appearance:** theme as a three-way pill control.
  - **Notifications:** the message sound.
  - **Privacy & data:**
    - **Shared links** lists the student's active share links, with Copy link and Stop sharing (the existing `/v1/shares` list and delete; a new `listShares()` client method);
    - Download your data;
    - Delete your data, with an explicit acknowledgement;
    - the university-consent promise as a note.
  - **Help:** Send feedback.
  - The account menu now holds only the student's identity and Sign out.

## 21 October: the agentic counselor (live audit P0/P1 and the founder's vision)

- **One voice, workers behind it.** The Counselor still speaks; background workers (research, the path analyzer) feed it. This is a fixed workflow (router plus workers), not an autonomous agent, so it stays testable and costed.
- **Research is decision support at any stage (founder).** Whenever the student asks a fact that helps them choose (fees, a field, places), research runs. Before, it ran only when the policy chose `answer_request`; when Voice itself promised "I will check" (`note_question`), nothing started. Now either starts the same idempotent `research.claim` job. Full research of every step of a chosen path stays PAI OS work.
- **Early directions (founder).** Voice may name one or two general fields as soon as the student's words point there, offered as ideas to test. Institutions and programs still need sourced research.
- **The 360-degree path analyzer** (`app/pai_c/paths/analyzer.py`, prompt `path_analyzer.md`, policy `path_analyzer.json`, migration 112):
  - It runs as a background job when the student asks for help deciding (`decision_help`), when they confirm the Mirror, when they press "Find my paths", or when they add their own path.
  - It runs once per input: the Truth Map version plus the paths the student typed in. A job that has not started yet is reused.
  - It suggests up to five general paths and checks each against the student, with four statuses:
    - 🟢 have;
    - 🟡 partial;
    - 🔴 blocker;
    - ⚪ unknown (founder).
  - Code, not the prompt, enforces honesty:
    - a known status without a valid evidence id becomes unknown;
    - paths or notes with a world number (the shared grounding pattern) are dropped or cleared;
    - dismissed paths never come back.
  - The student's own words travel with each verdict.
  - Analyzer paths are stored as `source="analyzer"`, `status="suggested"`; the student's own as `source="student"`, `status="saved"`. Re-adding a dismissed one restores it.
- **A path is a field of study (founder, after the first live look).** PAI is an education counselor, and the university side is about program fit, so every path generator now names fields as institutions name programs:
  - the analyzer, the planner's possibility and the Mirror lanes;
  - examples: a computing, data, business or design field, not "open a repair shop" or an apprenticeship.
  - When the evidence points to a kind of work, the path is the field of study that leads to it.
  - Code enforces the shape: 1 to 6 words, no slash, bracket or digit (`possibilities.json`, `valid_title`). One-word fields such as nursing are now valid.
  - The analyzer drops any title that fails.
  - The planner writes evidence as the student's words alone, without a speaker label or quotes. Rows stored before this change keep their old titles until dismissed.
- **Paths are a list, not big cards (founder).** Each row shows the field, why in one line, fit dots, status, Explore, Save and Not for me. The fit detail with the student's words is on the path page.
- **Overview never cuts content (founder).** "No scroll" meant one screen, not hidden content. The fixed layout now applies only through the `fit` variant (at least 64rem wide and 44rem tall, in `globals.css`). There the cards share the height, and the path list and the understanding card scroll inside themselves. Shorter windows scroll the page.
- **Workspace guide.** Voice may set `show_place` with a key from `workspace_places.json`. The reply then carries `workspace_place`, which chat renders as a link chip with the view's student-facing name. Unknown keys are ignored. The places list describes what the student finds, never how it works.
- **Conversation rules** (shared tail of both voice prompts): answer a direct ask first, give something concrete every reply, say a caution once, vary openings.
- **Journey stage.** The workspace projection reports the server stage, and `copy.json` `stageCaps` caps the journey step by it, so the journey no longer jumps from B to E on planned moments.
- **One operator stream per tab.** Components share one EventSource; hidden tabs hold none. This fixed the HTTP/1.1 connection exhaustion. Caddy/HTTP2 was not changed.
- **Composer.** Dropped characters could not be reproduced in 10 fast-typing runs; no change was made.
- **Profile.** The extractor is told to store stated marks as `result.marks_obtained` and `result.marks_total` (never a computed percentage) and the home city as `location.current_city`. The profile shows a "Please check" area for reconciler conflicts and invites a document upload for stated results. An education result now satisfies the "test result" basic.
- **Known gaps:**
  - background job messages (research replies) are English templates, not in the student's language;
  - institution names in analyzer titles are blocked only by the prompt, since there is no deterministic detector;
  - bare numbers without a currency or % sign are not caught as world numbers, because students state their own marks that way;
  - a profile record change alone does not trigger a fresh analysis until the Truth Map version or the student's paths change.
- **Docs.** Section 7 of `COUNSELOR_V3_PROMPTS.md` had drifted from `voice_guided.md`; it now mirrors the runtime prompt. The analyzer prompt has its own section, checked by a test.
