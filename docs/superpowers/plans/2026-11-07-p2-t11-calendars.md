# P2-T11 calendars: plan (R-20 with official data, R-26; row 6.20)

Spec §4.11 and §6.1 row T11 (code part only). Built on the integration branch (T1, T2, T3, T5, T8, T10) with T6 merged
(migration renumbered `os_0030`). No migration is needed for T11 (`os_0031` stays free).

**Not in this task:** the freeze-exception PR that moves `policy/academic_calendar.json` and `policy/admission_rules.json`
into Knowledge touches frozen Counsellor files and goes through the freeze process later. `check_freeze` must stay clean.
No real dates anywhere: every calendar here is a fixture.

## Design
- **Calendars are registry rows.** Kind `calendar` (T2) with `attrs.calendar_type` (`exam`, `result`, `admission`), parent an
  admission system, body or institution. `knowledge`-style vocabulary in `app/os/registry/calendars.yaml`: for each type
  the date fields it may hold and each field's fact class (`result_date` -> schedule date, closing dates -> deadline, ...).
  Instances (which board, which dates) are data that arrive through the import (T6).
- **Their dates are cycle-bound Knowledge facts** of scope `registry`, ref = the calendar id, per intake (term + year), value
  `{"date": "YYYY-MM-DD", "tz": "Area/City"}` (the shape the compiler already reads). `app/os/registry/calendars.py`
  records them (`record_calendar_date`: the field must belong to the calendar's type, the class comes from the
  vocabulary, `verified` only through review) and reads them (`calendar_dates`).
- **Reading:** `SqlKnowledge.registry_facts(refs, fields, intake_year, ...)` next to `programme_facts` / `route_facts`, with the
  same owner, term and labelled previous-year rules (P2-D24, R-26).
- **P1's `result_expected` reads an official calendar by registry id.** A playbook ask's `expected` may name a
  `calendar: cal:<id>` (the registry calendar) besides the route fact it names today; `fact` is then the calendar's
  field. The service reads those facts (`needed_calendars(playbook)`) and passes them to `compile_plan(calendar_facts=)`;
  `needs.expand` uses the registry fact when the ask names a calendar, else the route fact exactly as before (a playbook
  without `calendar` compiles byte-identically). The step's `fact_refs` carry `("registry", cal_id, field)`, so a
  changed calendar fact revises the plans that use it through `after_fact_change` (row 6.10 path), the date is
  provisional until the fact is confirmed (and any fact of another year is labelled), and the citation is the fact's URL.
- **Row 6.20** on a fictional student: the result-expected step is dated from the official calendar fact, then the
  provide step; after the date it is gone; a changed date revises the plan.
