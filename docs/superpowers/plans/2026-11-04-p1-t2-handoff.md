# P1-T2: versioned decisions and the hand-off — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every choice and withdrawal becomes a numbered decision version that reaches PAI OS exactly once (outbox in the same transaction, immediate delivery, version sweep), and a withdrawal stops the plan.

**Architecture:** The Counsellor writes a new `pai_route_decisions` row per version plus a `pai_os_outbox` row in the same session; the bridge delivers pending rows after the request commits and every ≤ 5 min. The OS stores each delivery by `decision_id` (one per version), applies only versions newer than the newest it applied for that student, and closes the plan with cause `withdrawn` on a withdrawn version. All of it only when `part_on("CONNECT_HANDOFF")` (T1) is true.

**Tech Stack:** Python 3.13, SQLAlchemy ORM (app) and Core (OS), Alembic (two trees), DBOS (OS worker), pytest (legacy suite on SQLite; `tests/os` on Postgres).

**Spec:** `docs/superpowers/specs/2026-11-04-p1-connection-core-design.md` §3.1 (and P1-D6, P1-D9). Master `docs/superpowers/specs/2026-11-03-pai-connect-design.md` R-02, R-03, R-06, R-12, R-79, §6 rows 6.1–6.4, 6.14.

## Global Constraints

- With `CONNECT_HANDOFF` off or the OS `counsellor` module off, the app behaves as today except that decision rows carry a version (no outbox rows, no delivery).
- DB changes only by Alembic: Counsellor tree `backend/alembic/versions/` (next: `124`), OS tree `backend/alembic/versions_os/` (next: `os_0018`); one head each (`python scripts/check_alembic_heads.py`).
- `app/os` never imports Counsellor code (Tach); all glue in `backend/app/pai_os_bridge.py`; Counsellor-side connection code in `backend/app/pai_c/connect/`.
- No country, institution or exam names in `app/os` Python (R-58). Fictional data only in tests.
- The export is `pai.decision_record.v2` (`app/os/contracts/decision_record_v2.py`, T1); `decision_id` = the version row's id.
- Never weaken a test; tests that pin today's behaviour stay green unchanged unless this plan names the change.
- `tach check` and `pytest tests/os` before pushing OS code; never run `tests/os` and the legacy suite at once.
- Tag tests with the R-IDs they prove; commit messages end with the session attribution lines.

## Decisions taken in this plan (rulings against spec §3.1; flagged to the owner in the PR)

- **D-a, `withdrawn_at` stays as a marker.** Spec §3.1 says old rows are never rewritten and the partial unique index is replaced. Every current reader (check-ins, journey, roadmap) finds "the active choice" by `withdrawn_at IS NULL`. So: versions are new rows and are never rewritten *except* `withdrawn_at` (a superseded marker, like today) and `steps_done` (checklist ticks, today's exception). The partial index `uq_route_decision_active` stays; a new unique index `(workspace_id, decision_version)` is added. A withdrawn version is inserted with `withdrawn_at = chosen_at`, so it is never "active".
- **D-b, intermediate waits for T5.** The OS plan engine takes the v1 `RouteContract`. The intake converts a v2 decision to v1 for the four v1 levels; an `intermediate` decision is refused `route_not_supported` until T5 adds v2 contracts to plans.
- **D-c, choice details come from T3.** `choose()` gains an optional `details: ChoiceDetails`. Until T3 builds the screens nothing passes it, so `os_supported` is false and the outbox row is `not_sent` (row 6.14: the OS does nothing).
- **D-e, re-choosing a withdrawn route.** Today a closed plan's route cannot get a new plan (`plan_closed`, a person decides). T2 keeps that; whether a re-choice after a withdrawal should open a fresh plan is left to the owner (raised in the PR).
- **D-d, journey id.** The export's `journey_id` is the student's active `counselor_decision` journey id; without one the outbox row is `not_sent` with `last_error = "no_journey"`.

## Review Focus

1. Two requests choosing at once for one student: versions stay unique and gap-free (the workspace `FOR UPDATE` lock); the loser gets today's 409. → Task 2 test.
2. Delivery fails (OS down) right after commit: the row stays `pending`, attempts counts up, the request still succeeds. → Task 5 test.
3. An older version delivered after a newer one (reordered sweep): the OS marks it `stale` and the plan follows the newer one. → Task 4 test.
4. Withdraw, then choose again: version n+2 starts a fresh plan (the withdrawn plan stays closed). → Task 4 test.
5. Rows created while the flag was off, then the flag and module are switched on: the sweep writes one outbox row for each student's newest version only. → Task 5 test.

**Interfaces:**
- Consumes: Task 3 `outbox.pending_for`, Task 4 `plan_source.submit_decision` / `latest_version`.
- Produces (`pai_os_bridge.py`):
  - `deliver_pending(db, workspace_id: str | None = None) -> dict` — for each pending `decision` row (oldest first): validate the payload as `DecisionRecordV2` (invalid → `not_sent`, `last_error="invalid_export"`), `submit_decision`, then `delivered` (also for `duplicate`/`module_off`: the OS holds it); on `OsUnavailable` stop and leave rows pending; on other errors `attempts += 1`, `last_error = <exception class name>`, continue. Commits its own changes. Returns `{"delivered": n, "failed": n, "not_sent": n}`. No-op when `part_on("CONNECT_HANDOFF")` is false.
  - `sweep_once(db)` — replaces `_submit_since_mark` with: `deliver_pending(db)`; then, per student whose newest decision version is above `plan_source.latest_version(student_ref)` and whose newest row has no outbox row, `outbox.record(db, newest)` and deliver it. Escalation delivery (`_deliver`) unchanged. `decision_changed`, `current_export` and `_submit_since_mark` are removed (no caller outside the bridge tests; `EXPORT_MODULE` goes with them).
- `routers/roadmap.py` `_write`: after `db.commit()`, call `pai_os_bridge.deliver_pending(db, workspace_id)` inside `try/except Exception` (logged; never fails the request). `_write` gains the `workspace_id` argument.
