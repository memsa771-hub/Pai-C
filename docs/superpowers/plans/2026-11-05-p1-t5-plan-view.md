# P1-T5: the roadmap shows the OS plan — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** For a route the OS runs, the Counsellor roadmap's chosen route shows the OS plan, with steps, status, due dates and "what changed", in today's `RoadmapPage.chosen` shape. A tick on an OS step completes the OS task. OS plan events reach the student as notifications, never chat. The intermediate level can be planned. Routes the OS can't run keep the labelled checklist.

**Architecture:**
- An OS builder makes `plan_view.v1` from the plan tables, choosing the plan through the intake rows (decision version → plan).
- A `PlanActions` port completes a student step through the same function the OS inbox uses.
- The bridge exposes both.
- A Counsellor adapter turns `PlanViewV1` into today's chosen-route shape behind `CONNECT_ROADMAP_FROM_PLANVIEW`.
- Kernel events are written to the OS `counsellor` outbox as `os_event.v1`. The bridge turns them into app notifications.

**Tech Stack:** Python 3.13, SQLAlchemy (app ORM, OS Core), DBOS worker, Next.js, pytest/vitest.

**Spec:** `docs/superpowers/specs/2026-11-04-p1-connection-core-design.md` §3.6 and the T2 decision D-b. Master: R-01, R-04, R-44, R-45; §6 rows 6.1–6.3, 6.11, 6.14, 6.18. The code map is in the session scratchpad and is carried into the SDD workspace.

## Global Constraints

- **Flags off means today, byte for byte.**
  - With `CONNECT_ROADMAP_FROM_PLANVIEW` off, `/v1/roadmap`, `/v1/roadmap/steps` and every serialize caller are byte-identical to today.
  - With `CONNECT_CHECKINS_FROM_PLANVIEW` off, check-ins are unchanged.
  - The adapter is one `part_on(...)` check made before any OS call.
- **Shape and frozen data.**
  - `RoadmapPage.chosen` keeps today's keys (`CHOOSE_KEYS`); new fields are optional and additive only (R-44).
  - `plan_view.v1` and `os_event.v1` are frozen; use them as they are.
  - `pai_c/policy/*.json`, `roadmap.json`, `pai_c/**/*.md` and `deep/**` are frozen.
- **No chat messages from the OS (R-45).** Plan events become screens and notifications only; never call any chat or send path.
- **Imports, names and checks.**
  - `app/os` never imports Counsellor code (Tach); all glue lives in `backend/app/pai_os_bridge.py`.
  - No country, qualification or exam names in `app/os` Python (R-58).
  - Only the kernel changes tasks and plans.
  - DB changes go through Alembic only.
  - Run `tach check` and `pytest tests/os` before pushing OS code; never run them alongside the legacy suite.
  - Never weaken a test. Tag tests with R-IDs. Commit messages end with the session attribution lines.

## Decisions taken in this plan (rulings; flagged to the owner in the PR)

- **D-r, the frozen plan_view.v1 lacks citations and step needs.**
  - OS steps on the roadmap carry no rule/source link and no evidence badge in P1.
  - A `plan_view.v2` with citations is left to T9 (R-54) if needed.
  - Requests and documents stay `[]` until T8.
- **D-s, plan selection.** The plan for a student comes from `os_counsellor_intake`, keyed by student and decision version:
  - `planned`, `revised`, `replaced` or `paused` → the plan is shown;
  - `withdrawn` or `unsupported` → the closed plan, state `stopped`;
  - `pending`, `held`, `refused`, `stale` or no row → state `empty`.
  - `decision_version` in the view is the newest version applied to that plan.
- **D-t, ticks.**
  - An OS step is tickable when it is student-owned, `waiting_student`, `inbox_kind` is `act` or `provide`, and it is not a review step.
  - Unticking an OS step is refused (409 with a plain message).
  - Completion uses one shared OS function, extracted from the inbox route, so the review guard and the visa-date recompute always run.
  - Ticking an OS step needs a signed-in human account, as the OS inbox already requires.
- **D-u, intermediate.** Plans accept `RouteContractV2`:
  - stored v1 plans keep parsing as v1;
  - only an `intermediate` decision uses v2;
  - the `route_not_supported` refusal for intermediate is removed;
  - `supports()` checks the playbook only.
  - `plan_summary` returns `None` for an intermediate plan, because `plan_summary.v1` is frozen to four levels and has no Counsellor reader.
- **D-v, OS events.**
  - The kernel writes `os_event.v1` rows to the OS `counsellor` outbox (template `os_event`) in the same transaction, only while the `counsellor` module is on.
  - `plan_finished` gets an event.
  - The escalation reader filters to template `escalation`, so it does not break.
  - The bridge turns each event into one app notification (`notify_once`, dedupe by event key). The fixed copy lives in `backend/app/pai_c/connect/os_event_texts.yaml`.
  - Event delivery runs when `CONNECT_ROADMAP_FROM_PLANVIEW` is on.
- **D-w, "PAI can't run this plan yet".** The chosen route card shows that banner when `choice.os_supported` is false. Since `choice` exists only with the hand-off on or a consent on record, flags-off screens are unchanged.

## Review Focus

1. **A decision is chosen but the OS has not applied it yet.**
   - The roadmap shows the empty state with a "your plan is being prepared" note, never stale steps from an older version.
   - → Task 1 test.
2. **A student ticks an OS step twice, or ticks a review step.**
   - The second tick is a no-op, never an error loop. A review step is refused.
   - → Task 2 test.
3. **The OS worker emits many events at once.**
   - Each becomes one notification, and repeats are deduped.
   - → Task 4 test.
4. **A stored v1 plan, after D-u.**
   - It still revises and validates exactly as before.
   - → Task 3 test.
5. **The flag is turned off after the student used the OS roadmap.**
   - The roadmap returns to today's checklist view without errors.
   - → Task 5 test.
